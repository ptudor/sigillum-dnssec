Notes on the fixes:

1. Added `VerifyDenialRRSIGFromResponse` (verify **every** NSEC/NSEC3 RRset in the raw
   response against the zone DNSKEY set, fail-closed), wired both denial paths through
   it before setting `Verified = true`, and surfaced the proof on
   `RecordValidation.DenialProof`. New tests sign real NSEC responses and assert
   genuine signatures verify while tampered/forged or raw-less ones do not.
2. `.env.example` and the `CLAUDE.md` table now use the integer `_SECONDS`/`_MINUTES`
   names the code actually reads; `getEnvInt` logs a warning on an unparseable value
   instead of silently defaulting.
3. `extractClientIP` walks X-Forwarded-For right-to-left, skipping trusted-proxy hops,
   and returns the first untrusted entry (X-Real-IP fallback), so a client-supplied
   leftmost entry can no longer spoof the attributed IP.
4. Wildcard answers now require a verified NSEC (covering the queried name) or NSEC3
   (covering the next closer name) proof; the result records
   `Wildcard`/`WildcardProofVerified` and warns when the closest-encloser proof is
   missing, so such answers are no longer represented as fully verified on the record
   signature alone.
5. Deleted `ProvesDSAbsence`, `VerifyDNSKEYAgainstAnchor`/`FindMatchingAnchor`,
   `writeJSONError`, `QueryWithRetry`, and the always-zero DNS-query/zones-validated
   metrics; wired the `active_validations` gauge via inc/dec in both validate handlers;
   switched `X-XSS-Protection` to `0`. The DNSKEY-RRSIG reconstructed-records item was
   confirmed correct (not a bug) and left as-is.

## Overall verdict

The service is mechanically sound:

- `go build ./...`, `go vet ./...`, and `gofmt -l` are all clean.
- All four test packages pass (`.`, `internal/dns`, `internal/rdap`, `internal/validator`).
- A live smoke test worked end-to-end: `/healthz` returns `OK`, anchors load from
  file, a quick validation of `ptudor.net` returned `secure` over both the JSON API
  and the SSE stream, and RFC 7807 error responses are well-formed.

The REVIEW_53 hardening round genuinely landed — fail-closed DS digest verification,
proxy-trust CIDR gating, config validation for ticker safety, scoped cache headers,
server timeout/header hardening, and SSE write-failure cancellation are all real and
correct in the code.

**However**, one REVIEW_53 claim is not actually true in the code (finding #1 below),
and there are several additional production issues. None block a careful deployment
behind Apache, but #1 is a trust-correctness bug in security-sensitive output and
should be fixed before the tool is represented as cryptographically verifying denial
of existence.

## Significant findings

### 1. NSEC/NSEC3 denial proofs report "RRSIG verified" without verifying a signature  — HIGH

`VerifyNSECDenialWithRRSIG` (`internal/validator/nsec.go:37`) and
`VerifyNSEC3DenialWithRRSIG` (`internal/validator/nsec.go:173`) advertise "full RRSIG
verification" in their doc comments, but neither performs a cryptographic check. Each:

1. Confirms an RRSIG covering NSEC (type 47) / NSEC3 (type 50) exists.
2. Checks the RRSIG timestamps are currently valid.
3. Looks up a DNSKEY whose key tag matches (`signingKey := findDNSKEYByTag(...)`).
4. Sets `proof.Verified = true`.

The `signingKey` is fetched and then **never used** — `sig.Verify(...)` is never
called. `verifyActualRecord` (`internal/validator/validator.go:440-456`) then copies
that into the API/SSE response as `RRSIGVerified: true`.

**Impact:** For NXDOMAIN/NODATA answers, the tool tells clients a denial proof was
cryptographically verified when only key-tag + timestamp matching occurred. A zone
serving a forged or corrupt NSEC/NSEC3 signature (with a valid key tag and unexpired
window) is reported as verified. This is exactly the "overstated cryptographic
guarantee" class that REVIEW_53 items `R53-002` and `R53-204` claimed to eliminate.

**Fix:** The raw response bytes are already captured (`queryResult.RawResponse`) and a
working full-verification helper already exists (`VerifyRRsetRRSIGFromResponse` in
`dnssec.go:290`). Wire the denial paths through it — verify the NSEC/NSEC3 RRset
signature before setting `Verified = true`, and surface the failure when it doesn't
verify.

### 2. `.env.example` variable names do not match what the code reads  — HIGH (operational)

`LoadFromEnv` (`config.go:215-248`) reads integer-valued, suffixed names:

| `.env.example` ships        | Code actually reads (`config.go`)   |
|-----------------------------|-------------------------------------|
| `QUERY_TIMEOUT=5s`          | `QUERY_TIMEOUT_SECONDS` (int)       |
| `TOTAL_TIMEOUT=30s`         | `TOTAL_TIMEOUT_SECONDS` (int)       |
| `RATE_LIMIT_CLEANUP=5m`     | `RATE_LIMIT_CLEANUP_SECONDS` (int)  |
| `HEARTBEAT_INTERVAL=5m`     | `HEARTBEAT_INTERVAL_MINUTES` (int)  |

**Impact:** Anyone deploying via the documented `.env` gets silent defaults for these
four settings. The failure is doubly silent because `getEnvInt` (`config.go:389`)
swallows `strconv.Atoi` errors and returns the default rather than failing fast — so
even a correctly-named-but-malformed value is ignored without a log line.

**Fix:** Correct the example to the suffixed integer names (and update the matching
table in `CLAUDE.md`, which documents the duration-style names). Optionally, have
`getEnvInt` log a warning when a present env var fails to parse, instead of silently
falling back.

### 3. X-Forwarded-For spoofing through the trusted proxy  — MEDIUM

`extractClientIP` (`ratelimit.go:188`) trusts the **leftmost** XFF entry when the
request arrives from a trusted-proxy CIDR:

```go
ips := strings.Split(xff, ",")
clientIP := strings.TrimSpace(ips[0])   // leftmost = client-controlled
```

Apache (and most proxies) *append* the real peer to whatever `X-Forwarded-For` the
client sent. A remote client can therefore send `X-Forwarded-For: 1.2.3.4` and have
the validator attribute the request to `1.2.3.4`, evading per-IP rate limiting (and
polluting request logs) with an arbitrary spoofed address.

**Fix:** With a single known reverse proxy, prefer `X-Real-IP`, or take the
**rightmost** untrusted XFF entry (walk right-to-left, skipping trusted-proxy hops).
The leftmost-entry approach is only correct when every proxy in the chain is trusted
and sanitizes inbound XFF.

---

### 4. Wildcard-synthesized answers are reported `secure` with only a warning  — MEDIUM

`DetectWildcardSynthesis` (`dnssec.go:399`) correctly detects wildcard synthesis from
the RRSIG `Labels` field and emits a warning, but the zone status stays `secure`.
RFC 4035 §5.3.4 requires a wildcard-synthesized answer to be accompanied by an
NSEC/NSEC3 proof that the queried name has no direct (non-wildcard) match. Without the
closest-encloser check, a wildcard answer is accepted on signature alone.

**Fix:** Either implement the closest-encloser denial check for wildcard responses, or
explicitly document this as a known limitation and avoid labeling such answers as a
fully verified `secure` chain.

## Smaller issues

- **`ProvesDSAbsence` has a knowingly-broken NSEC3 branch** (`nsec.go:494`,
  specifically `:510`). Its own comment concedes it returns `true` for *any* NSEC3
  lacking the DS type bit without hashing/matching the queried name. It is currently
  **unused** (dead code), so the bug is latent — but it is a foot-gun if wired in
  later. Fix the hash-match logic or delete the function.

- **Dead code worth removing.** Unused across the tree: `writeJSONError`
  (`problem.go:51`), `QueryWithRetry` (`internal/dns/query.go:197`), `RecordDNSQuery`
  / `RecordZoneValidated` / `SetActiveValidations` (`metrics.go`), and
  `FindMatchingAnchor` / `VerifyDNSKEYAgainstAnchor` (`internal/dns/anchors.go:117,138`).
  The two anchor helpers additionally do **insecure key-tag-only matching** and are a
  temptation to call — recommend deleting them outright since `VerifyRootTrustAnchor`
  (`dnssec.go:443`) already does digest verification correctly.

- **`active_validations` gauge is always 0.** `SetActiveValidations` (`metrics.go:166`)
  is never called from any handler. The SSE path correctly tracks
  `active_sse_connections` via inc/dec, but neither the JSON nor the SSE path updates
  the `active_validations` gauge. Either wire it up (inc on entry / dec on exit of both
  validate handlers) or drop the metric.

- **`X-XSS-Protection: 1; mode=block`** (`health.go:115`). Modern browsers ignore this
  header, and current OWASP guidance is to send `0` to disable the legacy auditor (it
  has caused XSS-style side channels in the past). Low impact given the strict CSP, but
  worth switching to `0` or removing.

- **DNSKEY-RRSIG verification uses reconstructed records, not raw wire bytes.**
  `VerifyDNSKEYRRSIG` (`dnssec.go:234`) rebuilds `dns.DNSKEY` records from the parsed
  struct with a hardcoded TTL of 3600 and verifies against a single signing key. This
  is *correct* for DNSKEY (miekg/dns recomputes the canonical form, and TTL doesn't
  enter the signature), but it is inconsistent with the newer raw-bytes approach
  (`VerifyRRsetRRSIGFromResponse`) used elsewhere. Not a bug — flagged only for
  consistency / future maintainability.

## What is solid

- Graceful shutdown with request draining and rate-limiter goroutine cleanup
  (`main.go`, `server.go:265`).
- Config validation rejects non-positive tickers/timeouts and malformed CIDRs
  (`config.go:293`), preventing `time.NewTicker` panics.
- HTTP server hardening: `ReadHeaderTimeout`, `ReadTimeout`, `MaxHeaderBytes` (1 MiB),
  bounded per-route write deadlines for non-SSE handlers, SSE intentionally exempt
  (`server.go:139,250`).
- Fail-closed DS digest comparison (`dnssec.go:31`) — no key-tag-only acceptance.
- RFC 6840 §5.11 multi-algorithm chain enforcement: every algorithm in the DS set must
  have a valid DS→DNSKEY link (`chain.go:170`).
- Trust-anchor verification computes and compares DS digests rather than trusting key
  tags, with collision handling (`dnssec.go:443`).
- 1 MiB cap on remote anchor fetch (`internal/dns/anchors.go:70`) and anchor validity
  filtering by `validFrom` / `validUntil`.
- SSE write-failure cancellation stops wasted validation work on client disconnect
  (`handlers.go:100`).
- RFC 7807 problem+json errors with request-id correlation and masked internal detail.
- Strict CSP, `nosniff`, `X-Frame-Options: DENY`, embedded static assets for
  single-binary deployment, RDAP out-of-band DS cross-check.
