### RDAYBLUEX-019 — State merge can erase same-generation CLI diagnostics — FIXED
- **Change (signer):** `ZoneState` gained a persisted monotonic `revision` (`omitempty`; old documents load at 0). `State` keeps the last synchronized disk image per zone (`base`, a deep copy taken at `LoadState`, `ReplaceFromDisk`, `ReloadFromDisk` and after every committed `Save`). `ReloadFromDisk` is now a three-way merge against that base instead of the `LastSigned`/`rolloverEqual` heuristic: a zone the disk did not change keeps memory (unsaved work included); a zone memory did not change adopts the disk; a zone both changed is merged per field class — signing fields follow the later `LastSigned` (disk on a tie), key identities and the full rollover record follow the disk (the later, key-file-consistent actor) and force a re-sign, publication fields follow the later confirmed generation with cache horizons never lowered and `PendingPublication` recomputed whenever signing and publication come from different sides, and warnings/errors are a three-way set merge in which a diagnostic either side removed stays removed and one either side added is kept (same-operation errors collapse to the disk's). A zone created independently on both sides adopts the disk copy; a zone the disk dropped without a removal marker is released only when memory holds nothing unsaved for it. `Save` advances the revision of every zone whose content differs from the base past both the in-memory and the base value before writing, and a committed write (including a `DurabilityError`) becomes the new base. `rolloverEqual` (type/phase/four key IDs) was replaced by `rolloverStateEqual` over every persisted field. `ReplaceFromDisk` and `ReloadFromDisk` share one validated disk read.
- **Files:** `internal/state/state.go`, `internal/state/rollover_equal_test.go` (rewritten for `rolloverStateEqual`), `internal/state/merge_rdaybluex019_test.go` (new), `state_merge_rdaybluex019_test.go` (new, root)

The CLI then clears them and the daemon's later saves (clean, and again with unsaved generation 3) do not resurrect them. Unit tests cover every class rule: unchanged disk keeps dirty memory, clean memory adopts disk, later signing wins in both directions, a disk-side publication confirmation of an older generation is adopted while the newer unsaved signing stays pending, CLI rollover timestamp/action changes are adopted without forcing a re-sign while a two-sided rollover transition adopts the disk record and forces one, `ForceResign` set by either side survives, removal markers and re-addition, independent creation, a revisionless old document merging by content and gaining a revision on save, and revision monotonicity across a failed save. CLI: `runPostSignHook` reports "served" by mode — hook mode: success confirms, failure leaves pending (unchanged); immediate mode: the atomic write already confirmed, so a failed hook only records the deployment error and returns true (DS automation is not blocked on the false premise that publication failed); probe mode: the hook (if configured) runs as the deployment mechanism and never confirms, the every-authoritative-server serial probe is run synchronously and is the sole authority, and an unconfirmed zone is reported as pending for the daemon/next `sign`. `runSign` applies the same rule through `recordHookResultCLI` and, in probe mode, probes every pending zone (including ones left pending by earlier runs). Explicit immediate mode with a hook: `PublishedAt` equals `LastSigned` immediately after signing, hook completion does not move it, a failed hook on the next generation leaves the zone published/not pending with a persisted `deployment:` error and never lowers a cache horizon, and a later successful hook clears the error without moving timestamps. ### RDAYBLUEX-018 — Pending hooks can overlap without a process-wide bound — FIXED

### RDAYBLUEX-004 — `data_dir` hot reload moves state without moving the lifetime lock — FIXED
- **Change (signer):** `data_dir` is restart-required. `Daemon.Reload` now returns an error and rejects, before touching anything, a configuration whose `DataDir` is not the active one (`ErrDataDirChanged`): identity is decided by `sameDirectory` — absolute + symlink-resolved path equality, or `os.SameFile` on the two directories — so symlink-equivalent, relative/absolute-equivalent and trailing-separator spellings are accepted while a different or unresolvable directory is refused. A rejected reload applies nothing (no zones, paths, listeners, hooks, heartbeat or state; the generation is not bumped) and logs a precise restart-required error naming both directories (no secrets). The SIGHUP branch in `runServe` performs the same check *before* `loadStateLocked(newCfg)`, so the other directory is neither locked nor read, and logs and continues on rejection. The config schema, CLI flags, on-disk state schema and startup locking are unchanged; hot migration was not implemented (the review allows it only with a full lock-transfer transaction, which is not needed here). Note: the review's suggested fix order omits this finding; it was taken here because it lives in the same `Reload` path as RDAYBLUEX-005/025.
