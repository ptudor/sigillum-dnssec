## Phase 1 — Regression boundaries and containment of false Secure verdicts

### RA6X-007 — Unsigned Additional DS records can authenticate an attacker-controlled child — FIXED
- **Change (Golang-dnssec-validator):** Every parsed record now carries `Owner`, `Class` and `Section` (`answer`/`authority`/`additional`; additive `omitempty` JSON fields), produced by new per-section converters in `internal/dns/records.go` that `parseResponse` uses section by section instead of merging first. Added an authenticated-data layer (`internal/validator/authenticated.go`): `VerifyRRsetFromResponse` evaluates every covering RRSIG as an indivisible candidate (owner, signer, validity window, crypto under each eligible same-tag key) and returns a `VerifiedRRset` holding the exact wire records and the exact signature that verified; `VerifyDNSKEYRRsetFromResponse` verifies the zone's Answer-section DNSKEY RRset over the wire against the authenticated keys; `VerifyDenialRRsetsFromResponse` verifies Answer/Authority NSEC/NSEC3 RRsets and returns only those that verified (Additional is never a candidate; unverifiable RRsets are reported and excluded, not promoted and not allowed to poison a genuine proof). The DS path now returns a `parentDSResult` separating the served Answer-section child-owned DS RRset (diagnostic `ZoneResult.DS`) from the exact authenticated DS RRset; only the authenticated set enters `ValidateChainLink`, `CollectDSMatchedKeys`, the RDAP comparison and `ChainLink.ParentDS`, and the DS signature must name the actual parent zone as signer. The parent for the DS query is the zone preceding the child in the walked hierarchy (`parentZoneFromHierarchy`) so the signer requirement is correct for label-skipping delegations. `ZoneResult.DNSKEY` is the Answer-section RRset owned by the zone; DNSKEY RRSIG verification runs over the raw response rather than a reconstruction of the merged slice. Leaf verification selects RRSIG/CNAME candidates from the Answer section at the queried owner only; the NSEC/NSEC3 `WithRRSIG` wrappers, `verifyDSAbsence` and `verifyWildcard` run their semantic checks on the authenticated records only. The old `VerifyRRsetRRSIGFromResponse`/`AnyKey` helpers remain as thin wrappers over the new core. Two test seams were added for the hermetic harness (RA6X-050): `Resolver.SetDefaultPort` and an unexported `Validator.rootServers` override.
- **Files:** `internal/dns/records.go` (new), `internal/dns/types.go`, `internal/dns/query.go`, `internal/dns/resolver.go`, `internal/dns/dialaddr_test.go`, `internal/dns/sections_ra6x007_test.go` (new), `internal/validator/authenticated.go` (new), `internal/validator/dnssec.go`, `internal/validator/validator.go`, `internal/validator/nsec.go`, `internal/validator/verification_fixes_test.go`, `internal/validator/harness_test.go` (new), `internal/validator/ds_section_ra6x007_test.go` (new)
- **Verification:** The review's probe is reproduced through the real `validateZone` path with the hermetic harness: a genuinely signed `child.test. ### RA6X-016 — Trusted key material loses its zone identity during signature verification — FIXED
- **Change (Golang-dnssec-validator):** Trusted keys now carry their authenticated zone (`DNSKEYRecord.Owner`, set by the parser and threaded through `ZoneResult.DNSKEY` → next zone's parent keys). `trustedKeyForSigner` refuses to place an owner-bearing key at any signer name other than its own zone, so verification never rewrites a key's owner to make a signature fit; `keyBelongsToZone` is applied in `CollectDSMatchedKeys` (a key parsed at another owner is never "the child's key" even when the DS digest computed at the child matches its material) and `CollectAnchorMatchedKeys` (root keys must be owned by `.`). `VerifyDNSKEYRRSIGByKeys` takes the expected zone and requires the RRSIG signer/owner and every RRset member's owner to be that zone; `VerifyDNSKEYRRsetFromResponse` already required owner and signer to equal the zone and verifies the original wire records. The DS signer must equal the actual parent zone (RA6X-007). Denial verification (`VerifyDenialRRsetsFromResponse`) now takes the zone whose keys are used and requires every accepted NSEC/NSEC3 RRset to be owned within that zone and signed by it; `VerifyNSECDenialWithRRSIG` gained a `zone` argument, `verifyDSAbsence`/`finalizeNoDSDelegation` take the parent zone, and `verifyWildcard` takes the leaf zone. Leaf A/CNAME verification calls `VerifyRRsetFromResponse` with the queried owner and the zone as required signer. Legitimate key reuse (the same key material at two zones, each signing its own data) and key-tag collisions remain accepted.

## Phase 2 — Unify signature selection and denial semantics

### RA6X-009 — Wildcard checks use metadata from a signature that never verified — FIXED
- **Change (Golang-dnssec-validator):** Leaf verification no longer picks the first covering RRSIG for its metadata. `verifyActualRecord` now calls `VerifyRRsetFromResponse` with all eligible zone keys (every covering signature at the queried owner is an indivisible candidate: owner, signer, validity window and crypto must all hold for that one signature), and the new `recordVerifiedLeaf` derives `SigningKeyTag`, `RecordCount` and the wildcard decision (`DetectWildcardSynthesis` → Labels) from the exact `VerifiedRRset.Signature` that verified. A candidate's successful crypto check can no longer validate another candidate's Labels/SignerName. The CNAME path uses the same engine. The old first-signature pre-checks (time validity, key lookup, signer check on the display record) were removed from the leaf path.
- **Files:** `internal/validator/validator.go`, `internal/validator/authenticated.go` (from RA6X-007), `internal/validator/signature_candidates_ra6x009_017_test.go` (new), `internal/validator/harness_test.go` (mock now preserves handler rcode)
- **Verification:** Through the real `verifyActualRecord` path with the hermetic harness: an authentic wildcard expansion (`*.child.test. A` served as `www.child.test.`, Labels 2) with an invalid same-tag RRSIG claiming Labels 3 prepended, appended, with a different SignerName, or both around the genuine one, is detected as wildcard from the verified signature and is **Bogus** without an NSEC no-exact-match proof and **Secure** (Wildcard, WildcardProofVerified, SigningKeyTag = verified key) with the proof, regardless of ordering. An ordinary exact-name answer stays Secure and non-wildcard, and a forged Labels-2 signature beside a genuine exact-name one does not mark it wildcard. `go vet ./...` clean; `go test -race -count=1 ./...` green.

### RA6X-017 — Unsupported DS algorithms and first-signature rejection produce false Bogus verdicts — FIXED
- **Change (Golang-dnssec-validator):** (1) Every eligible covering signature is tried as a whole: the leaf A/CNAME path (via RA6X-009's engine) and the NSEC/NSEC3 `WithRRSIG` denial wrappers, whose first-signature pre-checks (`findRRSIGForType` → time validity → `findDNSKEYByTag`) were deleted so an expired or unknown-key first signature no longer blocks a valid alternative; the wrappers dropped their now-unused parsed-RRSIG parameter (`VerifyNSECDenialWithRRSIG(qname, qtype, nsec, keys, zone, raw, rcode)`, likewise NSEC3). (2) Added `SupportedDNSKEYAlgorithm`, `SupportedDSDigestType` and `SupportedDSRecords`; after the parent has authenticated the DS RRset, `validateZone` classifies it and, when no DS uses a supported algorithm and digest type, sets the zone **Insecure** with an explanatory warning (RFC 4035 §5.2 / RFC 6840 §5.2) instead of Bogus; each unsupported DS is warned about; chain matching uses only the supported subset, so a supported path that fails is still Bogus. The classification runs only on the authenticated RRset, so an unauthenticated extra DS can neither downgrade nor rescue a chain.
- **Files:** `internal/validator/dnssec.go`, `internal/validator/validator.go`, `internal/validator/nsec.go`, `internal/validator/denial_rrsig_test.go`, `internal/validator/nsec_test.go`, `internal/validator/zone_identity_ra6x016_test.go` (call sites), `internal/validator/signature_candidates_ra6x009_017_test.go` (new)
- **Verification:** Permutations of expired, unknown-key, invalid-bytes and valid signatures with different key tags all verify via the valid one under A, CNAME, NSEC NXDOMAIN and NSEC3 NODATA through the real leaf path, in every order; an RRset with only expired/unknown-key signatures still fails, and an NSEC signed only by an expired signature fails with the validity-period reason. DS classification through `validateZone`: only-unsupported DS (ED448 algorithm, GOST digest) → **Insecure** with the no-supported-path warning; unsupported plus a good supported DS → **Secure**; unsupported plus a supported DS with a wrong digest → **Bogus**; an unsupported DS injected unsigned in Additional beside a genuine chain → **Secure**. `go vet ./...` clean; `go test -race -count=1 ./...` green.
