## Phase 1 — Regression boundaries and containment of false Secure verdicts

### RA6X-007 — Unsigned Additional DS records can authenticate an attacker-controlled child — FIXED
- **Change (Golang-dnssec-validator):** Every parsed record now carries `Owner`, `Class` and `Section` (`answer`/`authority`/`additional`; additive `omitempty` JSON fields), produced by new per-section converters in `internal/dns/records.go` that `parseResponse` uses section by section instead of merging first. Added an authenticated-data layer (`internal/validator/authenticated.go`): `VerifyRRsetFromResponse` evaluates every covering RRSIG as an indivisible candidate (owner, signer, validity window, crypto under each eligible same-tag key) and returns a `VerifiedRRset` holding the exact wire records and the exact signature that verified; `VerifyDNSKEYRRsetFromResponse` verifies the zone's Answer-section DNSKEY RRset over the wire against the authenticated keys; `VerifyDenialRRsetsFromResponse` verifies Answer/Authority NSEC/NSEC3 RRsets and returns only those that verified (Additional is never a candidate; unverifiable RRsets are reported and excluded, not promoted and not allowed to poison a genuine proof). The DS path now returns a `parentDSResult` separating the served Answer-section child-owned DS RRset (diagnostic `ZoneResult.DS`) from the exact authenticated DS RRset; only the authenticated set enters `ValidateChainLink`, `CollectDSMatchedKeys`, the RDAP comparison and `ChainLink.ParentDS`, and the DS signature must name the actual parent zone as signer. The parent for the DS query is the zone preceding the child in the walked hierarchy (`parentZoneFromHierarchy`) so the signer requirement is correct for label-skipping delegations. `ZoneResult.DNSKEY` is the Answer-section RRset owned by the zone; DNSKEY RRSIG verification runs over the raw response rather than a reconstruction of the merged slice. Leaf verification selects RRSIG/CNAME candidates from the Answer section at the queried owner only; the NSEC/NSEC3 `WithRRSIG` wrappers, `verifyDSAbsence` and `verifyWildcard` run their semantic checks on the authenticated records only. The old `VerifyRRsetRRSIGFromResponse`/`AnyKey` helpers remain as thin wrappers over the new core. Two test seams were added for the hermetic harness (RA6X-050): `Resolver.SetDefaultPort` and an unexported `Validator.rootServers` override.

Leaf A/CNAME verification calls `VerifyRRsetFromResponse` with the queried owner and the zone as required signer. Legitimate key reuse (the same key material at two zones, each signing its own data) and key-tag collisions remain accepted.

## Phase 2 — Unify signature selection and denial semantics

### RA6X-009 — Wildcard checks use metadata from a signature that never verified — FIXED
- **Change (Golang-dnssec-validator):** Leaf verification no longer picks the first covering RRSIG for its metadata. `verifyActualRecord` now calls `VerifyRRsetFromResponse` with all eligible zone keys (every covering signature at the queried owner is an indivisible candidate: owner, signer, validity window and crypto must all hold for that one signature), and the new `recordVerifiedLeaf` derives `SigningKeyTag`, `RecordCount` and the wildcard decision (`DetectWildcardSynthesis` → Labels) from the exact `VerifiedRRset.Signature` that verified. The old first-signature pre-checks (time validity, key lookup, signer check on the display record) were removed from the leaf path.

### RA6X-017 — Unsupported DS algorithms and first-signature rejection produce false Bogus verdicts — FIXED
- **Change (Golang-dnssec-validator):** (1) Every eligible covering signature is tried as a whole: the leaf A/CNAME path (via RA6X-009's engine) and the NSEC/NSEC3 `WithRRSIG` denial wrappers, whose first-signature pre-checks (`findRRSIGForType` → time validity → `findDNSKEYByTag`) were deleted so an expired or unknown-key first signature no longer blocks a valid alternative; the wrappers dropped their now-unused parsed-RRSIG parameter (`VerifyNSECDenialWithRRSIG(qname, qtype, nsec, keys, zone, raw, rcode)`, likewise NSEC3). ### RA6X-012 — NSEC3 proofs omit delegation boundaries and opt-out security semantics — FIXED
- **Change (Golang-dnssec-validator):** New chain engine in `nsec.go`: `nsec3Chain.closestEncloser` performs the RFC 5155 §8.3 proof and retains the exact closest-encloser and next-closer records; a matched closest encloser with NS-and-no-SOA or DNAME is rejected (`nsec3RecordBoundary`); records with unknown flag bits are ignored and reported (`Ignored`, RFC 5155 §8.2). Opt-out is represented separately from verification: an NXDOMAIN whose next closer is covered by an opt-out record, and a wildcard proof whose next-closer cover is opt-out, verify with `NSECProof.OptOut = true`, and `recordValidationVerdict` maps an opt-out conclusion to **Insecure** (RFC 5155 §9.2), recorded as a warning rather than an error. `verifyDSAbsence` (NSEC3) now accepts a delegation match (NS, no DS, no SOA) as a secure insecure-delegation proof, and requires a complete closest-provable-encloser proof (closest encloser matched, next closer covered by an opt-out record) for opt-out DS absence; a bare cover, a non-opt-out cover, and a matching record that is not a delegation no longer prove anything. Existing statuses are unchanged; `opt_out`, `closest_encloser`, `next_closer` and `ignored` are additive JSON fields.
- **Files:** `internal/validator/nsec.go`, `internal/validator/validator.go`, `internal/validator/denial_semantics_ra6x010_013_test.go`
- **Verification:** Signed fixtures through the leaf path: the review's self-wrapping NSEC3 for `child.example.com.` (NS+DS) no longer denies `x.child.example.com.` (delegation-point reason), nor does an unsigned-delegation or DNAME encloser; the signed self-wrapping apex NSEC3 with Flags=1 yields `Verified=true, OptOut=true` and an **Insecure** verdict (Secure without opt-out); a wildcard answer whose next-closer cover is opt-out is **Insecure** and Secure with a plain cover; flags 2 and 3 are ignored with the unknown-flags reason; DS absence: an opt-out cover without a closest-encloser match fails, a complete three-record opt-out chain proves an insecure delegation with `OptOut`, the same chain without opt-out proves non-existence (not DS absence), a matching NSEC3 with the DS bit is rejected, and a matching delegation NSEC3 without DS proves a secure insecure delegation. `go test -race -count=1 ./...` green.
