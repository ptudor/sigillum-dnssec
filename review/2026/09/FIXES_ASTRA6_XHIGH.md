## Phase 1 — Regression boundaries and containment of false Secure verdicts

### RA6X-007 — Unsigned Additional DS records can authenticate an attacker-controlled child — FIXED
- **Change (Golang-dnssec-validator):** Every parsed record now carries `Owner`, `Class` and `Section` (`answer`/`authority`/`additional`; additive `omitempty` JSON fields), produced by new per-section converters in `internal/dns/records.go` that `parseResponse` uses section by section instead of merging first. Added an authenticated-data layer (`internal/validator/authenticated.go`): `VerifyRRsetFromResponse` evaluates every covering RRSIG as an indivisible candidate (owner, signer, validity window, crypto under each eligible same-tag key) and returns a `VerifiedRRset` holding the exact wire records and the exact signature that verified; `VerifyDNSKEYRRsetFromResponse` verifies the zone's Answer-section DNSKEY RRset over the wire against the authenticated keys; `VerifyDenialRRsetsFromResponse` verifies Answer/Authority NSEC/NSEC3 RRsets and returns only those that verified (Additional is never a candidate; unverifiable RRsets are reported and excluded, not promoted and not allowed to poison a genuine proof). The DS path now returns a `parentDSResult` separating the served Answer-section child-owned DS RRset (diagnostic `ZoneResult.DS`) from the exact authenticated DS RRset; only the authenticated set enters `ValidateChainLink`, `CollectDSMatchedKeys`, the RDAP comparison and `ChainLink.ParentDS`, and the DS signature must name the actual parent zone as signer. The parent for the DS query is the zone preceding the child in the walked hierarchy (`parentZoneFromHierarchy`) so the signer requirement is correct for label-skipping delegations. `ZoneResult.DNSKEY` is the Answer-section RRset owned by the zone; DNSKEY RRSIG verification runs over the raw response rather than a reconstruction of the merged slice. Leaf verification selects RRSIG/CNAME candidates from the Answer section at the queried owner only; the NSEC/NSEC3 `WithRRSIG` wrappers, `verifyDSAbsence` and `verifyWildcard` run their semantic checks on the authenticated records only. The old `VerifyRRsetRRSIGFromResponse`/`AnyKey` helpers remain as thin wrappers over the new core. Two test seams were added for the hermetic harness (RA6X-050): `Resolver.SetDefaultPort` and an unexported `Validator.rootServers` override.
- **Files:** `internal/dns/records.go` (new), `internal/dns/types.go`, `internal/dns/query.go`, `internal/dns/resolver.go`, `internal/dns/dialaddr_test.go`, `internal/dns/sections_ra6x007_test.go` (new), `internal/validator/authenticated.go` (new), `internal/validator/dnssec.go`, `internal/validator/validator.go`, `internal/validator/nsec.go`, `internal/validator/verification_fixes_test.go`, `internal/validator/harness_test.go` (new), `internal/validator/ds_section_ra6x007_test.go` (new)
- **Verification:** The review's probe is reproduced through the real `validateZone` path with the hermetic harness: a genuinely signed `child.test. DS` for key A in Answer plus an unsigned DS for attacker key B (same owner in Additional, unrelated owner in Additional, and same owner in Authority) with a child DNSKEY RRset signed only by B is now **Bogus** in all three placements and the injected DS never appears in `ZoneResult.DS` or the chain link; the identical response with only A's chain (and legitimate glue in Additional) is **Secure** with `ChainLink.ParentDS` equal to the exact authenticated DS. Also covered: an Additional-section DNSKEY is not part of the RRset (genuine RRset still Secure, injected key not promoted; RRset signed only by a non-DS-matched key is Bogus), the denial boundary (Additional NSEC ignored, Additional-only NSEC is no evidence, an unrelated unverifiable NSEC RRset is excluded without failing a genuine proof), a DS RRSIG naming another zone as signer is rejected, the leaf RRSIG must sit in the Answer section, and the parser's per-section metadata. `go vet ./...` clean; `go test -race -count=1 ./...` green across the module.

### RA6X-008 — A mixed anchor document bypasses the root-anchor pinning boundary — FIXED
- **Change (Golang-dnssec-validator):** Added `dns.GetActivePinnedAnchors`, the only anchor set a root authentication path may consume (currently valid AND exactly pinned). `validateZone`'s root branch now uses it for both the existential root check and the DNSKEY-signing key set, and `CollectAnchorMatchedKeys` itself skips every non-pinned anchor, so the filter is applied at the final trust decision and not only at ingestion. Loading still retains unpinned entries as diagnostic data (`/api/anchors`, `GetActiveAnchors`), but they can no longer contribute a key. Readiness (`/healthz`, `/health`) and the `dnssec_validator_root_anchors_active` gauge now count active pinned anchors, so a document with only unpinned active entries reports not-ready rather than up-and-unable-to-validate. Both shipped pins (KSK-2017 and KSK-2024) and their overlap remain accepted.
- **Files:** `internal/dns/anchors.go`, `internal/validator/dnssec.go`, `internal/validator/validator.go`, `health.go`, `main.go`, `internal/metrics/metrics.go`, `internal/dns/anchors_pinned_ra6x008_test.go` (new), `internal/validator/anchor_pin_ra6x008_test.go` (new), `health_test.go`, `handlers_test.go` (fixtures gained the `DigestType: 2` the exact pin requires)
- **Verification:** The review's probe is reproduced at both levels using the real IANA KSK-2017 public key (the test first proves its computed DS equals the pinned digest): with an anchor set holding the genuine pinned KSK-2017 DS plus an attacker DS matching an attacker root key, `VerifyRootTrustAnchor` still passes (genuine key present) but `CollectAnchorMatchedKeys` now returns only the pinned key and a DNSKEY RRSIG made only by the attacker key is rejected; through the hermetic harness, a root DNSKEY RRset containing the genuine KSK-2017 plus the attacker keys, signed only by the attacker, is **Bogus** in `validateZone`, and a set whose only active anchor is unpinned is **Indeterminate**. `GetActivePinnedAnchors` keeps both shipped pins and drops unpinned, tag-colliding, future and expired entries while `GetActiveAnchors` retains the diagnostics; an unpinned-only active set fails `/healthz`. A positive signature by the genuine root KSK cannot be produced hermetically (no private key); the positive path is covered structurally (the genuine key remains the sole anchor-matched signing candidate, and the crypto path is unchanged from the existing R-024 tests). `go vet ./...` clean; `go test -race -count=1 ./...` green.
