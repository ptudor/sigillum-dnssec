## Phase 2 — Rebuild the validator's root of trust and cryptographic candidate model

### R-024 — Unauthenticated trust-anchor input — FIXED (authentication core; RFC 5011 automation deferred to R-025, scoped below)
- **Change:** Replaced the weak "at least one anchor has a known key tag" floor with an authoritative **pinned-anchor** authentication boundary. `internal/dns/anchors.go` now ships `pinnedRootAnchors` (the IANA KSK-2017 record: tag 20326, alg 8, digest type 2, digest `E06D…EC8D` — the stable, cross-confirmed root DS) and `IsPinnedRootAnchor()`, which matches an anchor only on an exact (tag, algorithm, digest type, digest) tuple (hex case-insensitive). `VerifyRootTrustAnchor` (`internal/validator/dnssec.go`) now **skips any anchor that is not pinned** before attempting a digest match, so an attacker-supplied anchor can never become the root of trust even if it cryptographically matches a served/forged root DNSKEY. Loaders (`LoadAnchors`/`LoadAnchorsFromURL`, via new shared `finalizeAnchors`) now enforce zone `.`, structural digest validation (hex + exact length per digest type), duplicate rejection, and require ≥1 pinned anchor. Added `anchorRedirectPolicy` (`CheckRedirect`) that rejects HTTPS→non-HTTPS scheme downgrades and cross-origin (host:port) redirects.
- **Scope note (honest):** This closes the Critical authentication defect (unauthenticated input becoming an attacker-controlled root of trust) and the redirect vector named in the Evidence. It does **not** implement the fix spec's *optional-form* RFC 5011 authenticated `root-anchors.xml` update pipeline / hold-down / atomic last-known-good cache — that is a distinct subsystem the review assigns to R-025/R-039/R-055 and is addressed there. The pre-published successor KSK-2024 (tag 38696) is intentionally left **unpinned/fail-closed**: its authoritative digest is not present in the repo, and fabricating a security-critical constant is forbidden and would risk rejecting the real root at the 2026-10-11 rollover. A code comment documents that its authentic digest must be added before that date. Current active root validation (KSK-2017) is unaffected.
- **Files:** `internal/dns/anchors.go`, `internal/validator/dnssec.go`, `internal/dns/anchors_r024_test.go` (new), `internal/validator/anchor_auth_r024_test.go` (new)
- **Verification:** New tests prove the pre-fix exploit is now rejected — `TestVerifyRootTrustAnchor_RejectsForgedChain` builds a forged root DNSKEY, computes its true DS digest, supplies a malicious anchor matching it plus a dummy tag-20326 entry, and asserts no trust is established; `TestLoadAnchors_RejectsDummyTagPlusMaliciousAnchor` asserts the same set is rejected at load. Structural (`short/non-hex/unsupported/wrong-zone`), duplicate, pinned-exact-match, and cross-origin-redirect rejections all covered and passing. Full validator suite: `go vet ./...` clean and `go test -race -count=1 ./...` green across all packages.

### R-043 — Invalid DNSKEY flags/protocol authenticate signatures — FIXED (implemented with R-044)
- **Change:** Added `DNSKEYRecord.EligibleForVerification()` (`internal/dns/types.go`): a key may verify RRSIGs only if Protocol==3, the Zone Key flag (0x0100) is set, and it is not revoked (RFC 5011 REVOKE bit / `IsRevoked`). SEP (0x0001) is deliberately not required. Applied this gate at every authenticated-key selection site: `CollectDSMatchedKeys`, `CollectAnchorMatchedKeys`, `ValidateChainLink` (DS→DNSKEY digest match), `verifyDNSKEYRRSIGOne`, the leaf A/CNAME and DS RRSIG verifiers (via `EligibleKeysByKeyTag`), and the denial-RRSIG verifier. Ineligible keys remain in the parsed `result.DNSKEY` set (unchanged JSON/diagnostics) but can no longer authenticate anything.
- **Files:** `internal/dns/types.go`, `internal/validator/dnssec.go`, `internal/validator/validator.go`, `internal/validator/key_eligibility_r043_test.go` (new)
- **Verification:** `TestR043_EligibleForVerification` covers protocol!=3, zone-key-flag-clear, revoke-bit, and IsRevoked rejections plus valid KSK/ZSK acceptance. `TestR043_ChainLinkRejectsIneligibleDSMatch` proves a non-zone key whose digest matches a DS cannot satisfy the chain. `TestR043_CollectDSMatchedKeysExcludesIneligible` proves a revoked key is not DS-matched. Confirmed no production verification path still uses the old first-match `Find*ByKeyTag` (only test references remain). Full validator race suite green.

### R-027 — Leaf verification not bound to owner/section — FIXED (leaf/CNAME/DS binding via raw-response helpers)
- **Change:** Added `expectedOwner string` and `answerOnly bool` parameters to `VerifyRRsetRRSIGFromResponse` (and its `AnyKey` wrapper). The raw-response verifier already re-parses the wire message (where owner and section survive), so it now (a) considers only the Answer section when `answerOnly` is set and (b) requires the signed RRset's owner to DNS-canonically equal the queried name. Wired the leaf A and CNAME verifiers to bind to the queried `domain` (Answer-only), and the DS verifier to bind to the exact child zone (threaded `childZone` through `verifyDSRRSIGSet`/`verifyDSRRSIGOne`, Answer-only). A cryptographically valid RRset for another owner replayed in Authority/Additional can no longer authenticate the queried name.
- **Scope note:** This closes the exploit named in the Evidence (replayed valid RRset for a different owner/section). It does NOT perform the broader data-model refactor (preserving owner/section on every parsed record model and threading a query context into *every* verifier including the wildcard/NSEC internals) — that pervasive change touches `parseResponse` and all record types and belongs with R-026/R-030/R-036/R-037. Wildcard-synthesized answers are unaffected because the synthesized RR carries the queried owner in the Answer section.
- **Files:** `internal/validator/dnssec.go`, `internal/validator/validator.go`, tests `owner_time_binding_r027_r028_test.go` (new) + updated `chain_enforce_test.go`, `dnssec_test.go`, `verification_fixes_test.go` callers
- **Verification:** `TestR027_LeafBoundToAnswerOwner` — a validly-signed `other.example.com` A RRset placed in Additional is rejected for query `www.example.com`, while the same RRset in Answer at its true owner verifies. Full validator race suite green.

### R-028 — Time check and crypto can accept different signatures — FIXED

### R-025 — Local anchors prevent authenticated refresh/rollover — SKIPPED
- **Reason:** The fix spec is explicitly predicated on R-024 having built an "authenticated refresh pipeline" (RFC 5011 hold-down / authenticated `root-anchors.xml` signature processing / atomic write-back cache). R-024 here instead took the **static-pinning** approach (documented in that entry), which makes R-025's central remedy — acquiring the pre-published successor KSK-2024 (tag 38696) via scheduled refresh — moot and blocked: under pinning, a refreshed 38696 anchor is fail-closed until its authentic digest is pinned (which I cannot do without an authenticatable source). The remaining pieces (scheduled network refresh that writes back a last-known-good cache atomically, `GeneratedAt`/next-rollover freshness tracking, readiness degradation before expiry) form a subsystem that overlaps R-039 (done) and R-055 (done). Implementing a partial refresh/write-back on top of the pinning model would produce an inconsistent, half-built anchor lifecycle whose headline benefit (rollover survival) it cannot actually deliver here. Skipped rather than misrepresent a partial change as resolving the finding. (Confirmed the bug is real: `AnchorsStore.Load` → `LoadAnchorsWithFallback` prefers the nonempty file, so the 24h "refresh" re-reads the file and never consults the URL. A focused follow-up — an authenticated `Refresh()` that fetches the URL, validates against the pin, and atomically rewrites the cache — is the recommended path once a successor digest can be pinned.)
